# Ironvellum visual evolution — design specification

> **SUPERSEDED — scope changed 3 October 2026.** The owner chose to keep the existing layout and all current features. Only the social feed/Tidings and skill-tree technique illustrations remain in scope. The broader visual and art proposals below are retained for history and do not authorize implementation.

**Status:** proposed for owner review, 3 October 2026. This specifies a modest visual evolution of the existing Android app. The browser preview at `C:\Users\alexm\.codex\visualizations\2026\10\03\01a10155-d832-70e1-b787-3bfacee8cbf0\ironvellum-evolution.html` illustrates rhythm, art direction and a possible Tidings card; it is not a feature inventory or an approved replacement for any screen.

## Intent and boundaries

Make the Ledger easier to scan and more visually coherent while retaining its strong, game-like dark-fantasy identity. Preserve every current capability, route, state, data rule and reward path. This is a visual and interaction-polish project, not a reset of information architecture or game mechanics. Existing terms in `docs/GLOSSARY.md` are authoritative for all user-facing copy; in particular, Today, Rites, Ledger, Codex, Allies, Trial, Chronicle, Deed, Path, Tidings, Missives, Circle, Reckoning and Veil keep their distinct meanings. Plain safety, privacy, scientific and settings words remain plain.

The app stays offline-capable for its local training/game experience. Generated illustrative art is bundled with the APK; no runtime image generation or paid service is introduced. User-uploaded social media is a separate gated extension described below. Existing navigation IDs, persistence models, cloud wire values and glossary-protected IDs must not be renamed as part of visual work.

## Visual language

Build from `ui/theme/Theme.kt`, not a new competing theme. Its current warm charcoal papers are `Abyss #0C0C0B`, `Vault #171715` and `VaultHigh #1E1E1B`; primary bone ink is `#E8E8E4` and muted ink `#A3A099`. `Emerald #34D399` marks XP/success, `SystemGreen #6FAE8C` is the quieter accent, and `SovereignGold #F2C14E` belongs to earned moments. Preserve Chakra Petch, sanctioned tracking values, inked edges and chamfered silhouettes. The INK/CLEAN preference remains meaningful: both modes retain layout and capability; ink adds texture/edge character while CLEAN uses restrained rendering.

Composition should use one obvious primary action per view, a readable heading and content order, and compact secondary metrics. More whitespace is useful only if it does not push daily or live-training controls into obscurity. Keep panel boundaries subtle, avoid blue-grey gradients and excessive gold, and never communicate a status through color alone. Audit hard-coded `#0D1110` dialog/sheet paper and primary/on-primary foreground pairings against the warm-charcoal tokens; treat them as review candidates, not automatic bulk substitutions. Contrast, text wrapping and selected semantics must be verified on devices. Preserve the current 48 dp target convention for interactive controls; small glyphs sit inside that target rather than reducing it.

The world remains a Ledger of Ironbound Trials, not a generic fantasy battle interface. Avoid armies or soldier-rank imagery, neon HUDs and parchment-beige screens. Keep the current glossary's narrator voice for loading, empty and error messages, with a plain next action. Do not rename visible glossary terms. Scientific measurements, accessibility labels and privacy choices take priority over flavor.

## Art contract

Create a small coherent family of bone-ink/sumi-e figures, seals and brush textures on transparent or warm-black backgrounds. Figures must read as intentional silhouettes at phone scale, with consistent anatomy, pose weight, lighting direction and stroke density. The previously explored anatomical engraved-study look is **not approved as final art**; only an individually reviewed sample that satisfies the dark-fantasy silhouette brief may inform final assets. Use art as atmosphere, section marker or empty-state illustration, never as the sole way to understand a value, action, rarity or ownership. Preserve existing crest identity and rarity/level/frame rules in `LifterIdentity.kt`.

Assets are generated and optimized before release, bundled in Android resources and available offline. No runtime AI endpoint, generation SDK or paid font/art service. **Proposed engineering budget, pending owner review:** compare compressed APK/AAB size to the pre-change build and aim to cap incremental packaged art at **8 MiB** for the first release. If a coherent set cannot meet that cap at useful quality, reduce the set or present the measured trade-off for owner review; do not silently ship larger assets. Inspect 1× and high-density rendering, light/dark contrast within the dark theme, screen-reader text alternatives where art carries information, motion-reduction behavior, and scroll performance on the owner's target device. Decorative art has no spoken label.

## Tidings media boundary

The approved near-term change is layout polish of existing text/data cards, retaining every present feed detail, privacy rule and action. The preview's image + Trial arrangement is direction for a **possible later photo-capable card**, not permission to invent upload infrastructure. The current `LifterIdentity.kt` accepts `avatarUrl` as a reserved parameter but renders a generated crest; the code inspection found no functioning social photo upload/loader path. Tidings must continue to look finished with no photo, a failed media load or a private post. Where a future image exists, its crop must not conceal the Trial name, movements, totals, time, audience, tribute or remark actions.

Before enabling user photos, prepare a separate bounded product/engineering decision with measured monthly storage, transfer and request projections at plausible usage levels; explicit per-account and per-post limits; client compression and thumbnail dimensions; cache policy; abuse/report handling; and deletion consistency when a Trial, account or shared audience is removed. Verify authorization and signed URLs or equivalent privacy enforcement for Public, Allies only and Private, including stale caches and revoked allies. Identify the host and documented free/paid limits, and obtain owner approval for any recurring-cost or deployment decision. Do not promise zero recurring cost or add a paid service under this visual spec. Photo work is excluded from the first implementation slice unless this gate is satisfied and separately approved.

## Rollout and acceptance

Implement in reviewable slices: shared tokens/components and representative art; Today/Rites/Ledger; Codex/Veil; Allies text-only polish; then a final consistency pass. This is a design rollout boundary, not an implementation task list. A slice may change presentation, spacing and copy that follows the glossary; it may not remove a screen, hide a previously discoverable action, change calculations, replace cloud data rules or alter reward odds. Keep local training usable with no cloud configuration. Stage media separately. If work is delegated to subagents in later implementation stages, use `gpt-6-sol` as the owner requested.

For each touched screen, the implementation plan must enumerate the current interactive controls, dialogs, tab/route entries and visible states against the source at that time, then map each to its resulting location. Include first-run Binding, signed-out, offline/unconfigured, empty, loading, stale, error and populated examples. Capture before/after screenshots at the same viewport and font scale, plus a control-reachability checklist. Validate talkback order, selected tab state, at least 48 dp touch bounds, long true names/movement names, narrow phones, and color contrast. The screen inventory above starts that audit but cannot substitute for it.

Run the repository's **local** gate (`python3 tools/gate.py`, with `--backend` when backend behavior changes); never add push/PR GitHub Actions triggers. Instrumented tests use the gate's emulator lock and emulator serial, never the owner's physical phone. For visual review, inspect the built app on emulator and a safe install on the owner's phone where available. Confirm no regressions in navigation/deep links/notifications, Trial sealing and Chronicle data, Deed/Path/Veil rewards, social privacy and moderation, appearance preference and account safety. A visual pass is complete only when functionality parity, accessibility and measured package-size checks pass alongside the design review.
